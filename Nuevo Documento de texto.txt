Objetivo y Arquitectura Orientada a Objetos (SOLID)Se implementó un módulo de procesamiento de pagos en Python aplicando diseño orientado a objetos y principios SOLID (especialmente Responsabilidad Única y Principio de Inversión de Dependencias):Orden: entidad de datos (@dataclass) con id, monto, token_pago y estado.RepositorioOrdenes: abstracción (ABC) para obtener y guardar órdenes sin acoplar el núcleo del negocio a una base de datos real.PasarelaPago: abstracción (ABC) para ejecutar el cobro sin depender de una API externa real.ServicioPagos: clase de negocio que valida montos, aplica reglas de cálculo, invoca la pasarela y actualiza el estado de la orden.2. Ciclo TDD (Red - Green - Refactor)Fase Roja (Red): Se redactaron primero las pruebas unitarias en test_servicio_pagos.py antes de completar la lógica, verificando fallos iniciales cuando la implementación aún no cumplía los escenarios esperados.Fase Verde (Green): Se implementó la lógica mínima en servicio_pagos.py y se ejecutó python -m unittest discover -v, obteniendo la ejecución exitosa de todas las pruebas (Green bar).   Refactor: Se organizaron las responsabilidades separando interfaces abstractas y encapsulando el cálculo del monto en _calcular_monto_final sin alterar el comportamiento externo.3. Uso de Mocks y StubsMediante unittest.mock.MagicMock se aislaron RepositorioOrdenes y PasarelaPago:Stubs: Se configuró return_value en obtener_orden (retornando una Orden o None) y en cobrar (True o False) para simular respuestas de base de datos y pasarela.Mocks: Se verificaron interacciones críticas con assert_called_once_with y assert_not_called (por ejemplo, asegurando que no se cobre ni se guarde si la orden no existe).4.
